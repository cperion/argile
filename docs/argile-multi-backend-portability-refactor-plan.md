# Argile Multi-Backend Portability Refactor Plan (Love2D, raylib, SDL3)

## Status / Intent

This document defines a **full portability refactor plan** to make Argile portable across multiple renderer/platform backends while preserving Argile's core design:

- Argile core remains a backend-neutral UI engine that emits render commands.
- Terra language frontends (V2/V3) remain compile-time authoring layers.
- Backends (Love2D, raylib, SDL3) become thin adapters over a stable C ABI/render-command contract.

This is a **design-first refactor**. Backward compatibility is not the priority. Coherence, correctness, and a clean architecture are the priority.

The goal is not just backend parity. The goal is **portable, demonstrably correct end-to-end behavior**.

## Current State (Repository Snapshot)

### Core / Language

- Backend-neutral runtime in `src/` (`context`, `config`, `layout`, `builder`, `init`, etc.)
- V2 language extension: `src/lang/argile.t`
- V3 language + AST + lowering:
  - `src/lang/argile_span.t`
  - `src/lang/argile_v3_ast.t`
  - `src/lang/argile_v3.t`
  - `src/lang/argile_v3_lower.t`
- Stable C/FFI export surface generated by `tools/build_argile.t`
- Generated outputs:
  - `build/libargile.so`
  - `build/argile_api_ffi.lua`
  - `build/argile_api.h`

### Render Commands / Runtime Features Already Present

Argile already emits a backend-neutral render command stream including:

- `RENDER_RECTANGLE`
- `RENDER_BORDER`
- `RENDER_TEXT`
- `RENDER_PAINT`
- `RENDER_CUSTOM`

And supports runtime UI state overlays via context APIs:

- `hover`, `active`, `focus`, `selected`, `disabled`

### Existing Demo Backend

- Love2D demo exists at `demo/love/`
- It currently loads `build/libargile.so` via LuaJIT FFI and renders Argile commands
- A Terra V3 scene export exists in `demo/love/v3_bridge.t` via `LoveDemoV3Frame(...)`

### Problem in Current Demo Structure

The Love2D demo proves the concept, but it is currently **demo-specific and backend-coupled**:

- `LoveDemoV3Frame(...)` is a Love-specific scene export signature (`width`, `height`, mouse position, pointerDown)
- Build script includes demo exports directly into the core lib as a special-case
- Renderer/input/text-measure code lives in one Love file (`demo/love/main.lua`)
- No backend-neutral scene ABI contract yet
- No backend adapter layout for raylib / SDL3

This refactor addresses that.

## Refactor Objectives (Hard Requirements)

1. **Backend-neutral core**
- `src/` must remain free of Love2D/raylib/SDL3-specific dependencies or branching.

2. **Portable scene invocation ABI**
- Replace backend-specific scene export shapes (e.g. `LoveDemoV3Frame(...)`) with a backend-neutral frame API.

3. **Backend adapters are thin and explicit**
- Each backend maps platform input + text measurement + render command drawing to Argile.
- No backend-specific semantics leak into V3 language or core runtime.

4. **Love2D, raylib, SDL3 first-class demos**
- All three backends must render the same Argile V3 scene(s) from the same exported scene functions.

5. **Correctness-focused validation**
- Not only "same behavior across backends", but also correctness of render command payloads/order and state behavior.

6. **Build isolation**
- `make build` must build core Argile without requiring Love2D/raylib/SDL3 SDKs.
- Backend demos build/run through separate targets.

7. **Clean architecture for future backends**
- WebGPU/OpenGL/Metal/Vulkan/software backends should fit the same adapter model later.

---

## Non-Goals (For This Refactor)

1. Implementing advanced text shaping (HarfBuzz, bidi, rich text)
- Backends may initially use their native basic text APIs.

2. Runtime theme switching in V3
- V3 tokens/recipes remain compile-time/lowering-time for now.

3. Backend-independent pixel-perfect visual identity
- Text rasterization and font rendering will differ between Love2D/raylib/SDL3.
- The correctness contract is command semantics + adapter fidelity, not identical pixels.

4. Replacing the existing Argile core runtime
- Core remains the execution engine.
- Refactor is around portability structure and adapter contracts.

---

## Design Principles (Authoritative)

1. **Argile Core Emits Commands, Backends Render Them**
- Argile does layout, hit-testing, and command generation.
- Backends do drawing and platform/input/text integration.

2. **Language Frontends Are Optional at Runtime**
- V2/V3 are compile-time authoring systems.
- Runtime only needs the core ABI and scene exports.

3. **Renderer and Platform Are Separate Concerns**
- A backend may combine them (Love2D/raylib), but the architecture should distinguish:
  - renderer adapter
  - platform/input adapter
  - text metrics adapter

4. **Stable ABI Boundary**
- `ui.capi` + generated header/FFI is the portability contract.
- Scene exports should be C-callable and backend-neutral.

5. **No Hidden Backend State in Core**
- Backend-specific objects (fonts, textures, windows, renderers) live outside Argile core.

6. **Correctness Before Convenience**
- Adapter tests must validate render-command interpretation and state behavior, not just “it draws something”.

## Portability Contract (Core ↔ Backends)

This is the most important part of the refactor.

### A. Core Runtime Contract (Existing + Standardized Usage)

Backends consume these core responsibilities via `ui.capi`:

- Context lifecycle
- Arena allocation
- Frame lifecycle:
  - `BeginLayoutForContext(...)`
  - scene emit function
  - `FinalizeLayoutForContext(...)`
- Render command buffer access
- Input/state setters
- Text measure callback registration

Existing core APIs already close to this contract include (examples):
- `BeginLayoutForContext`
- `FinalizeLayoutForContext`
- `GetRenderCommandBufferForContext`
- `SetPointerStateForContext`
- `SetElementFocusedForContext`
- `SetElementSelectedForContext`
- `SetElementDisabledForContext`
- `SetCurrentContext`
- `GetApiVersion`

### B. New Backend-Neutral Scene Export Contract (Required)

Current demo export:
```terra
terra LoveDemoV3Frame(width: float, height: float, mouseX: float, mouseY: float, pointerDown: bool) : int32
```

This is backend-specific and must be replaced by a backend-neutral frame API.

#### Proposed C ABI Structs (add to `src/config.t`, export via `ui.capi`)

```c
typedef struct ArgileFrameInput {
    float width;
    float height;

    float pointer_x;
    float pointer_y;
    bool pointer_down;

    /* Optional now, but reserve in V1 portability API if added immediately */
    bool pointer_pressed;
    bool pointer_released;

    float scroll_delta_x;
    float scroll_delta_y;
    float delta_time;
} ArgileFrameInput;

typedef struct ArgileFrameStateFlags {
    bool focused;
    bool selected;
    bool disabled;
} ArgileFrameStateFlags;
```

If the project prefers to minimize ABI churn, `pointer_pressed/released` and scroll/delta can be omitted from the first version and added later. However, the plan recommends adding them now because SDL3/raylib integrations will want them quickly.

#### Proposed Scene Export Signature (C-callable)

```c
int32_t ArgileDemoFrameForContext(struct ArgileContext* ctx,
                                  const struct ArgileFrameInput* in);
```

#### Optional Scene Control Helper (recommended)

For demos that expose toggles on known elements (like the V3 card demo):

```c
typedef struct ArgileDemoIds {
    ElementId card;
    ElementId title;
    ElementId body;
} ArgileDemoIds;

void ArgileDemoGetIds(struct ArgileDemoIds* out_ids);
```

This avoids hardcoding element-id hashing in each backend host and removes repeated string/FFI pitfalls.

#### Terra Equivalent (scene export implementation target)

```terra
terra ArgileDemoFrameForContext(ctx: &ui.Context, input: &ui.ArgileFrameInput) : int32
    ui.SetCurrentContext(ctx)
    ui.SetMeasureTextFunctionForContext(ctx, demo_measure_text, nil) -- new ForContext API (see below)

    var p: ui.Vector2
    p.x = input.pointer_x
    p.y = input.pointer_y
    ui.SetPointerStateForContext(ctx, p, input.pointer_down)

    ui.BeginLayoutForContext(ctx, input.width, input.height)
    [compiled_scene_quote]
    return ui.FinalizeLayoutForContext(ctx)
end
```

### C. Text Measurement Contract (Must Be Explicit)

Text is the main source of cross-backend layout drift. The portability refactor must make the contract explicit.

#### Current Core Capability
- `SetMeasureTextFunction(...)`
- `ResetMeasureTextCache()`

#### Required Refactor Improvement
Add `ForContext` variants to eliminate hidden reliance on current global context in backend hosts:

```terra
terra ui.SetMeasureTextFunctionForContext(ctx: &ui.Context,
                                          measureTextFunction: MeasureTextFnType,
                                          userData: &opaque)
terra ui.ResetMeasureTextCacheForContext(ctx: &ui.Context)
```

Export via `ui` and `ui.capi` and regenerate `build/argile_api.h` / `build/argile_api_ffi.lua`.

#### Backend Rule (Authoritative)
The same backend text system must be used for both:
- measurement callback (`MeasureText`)
- text rendering (`RENDER_TEXT`)

Examples:
- Love2D: `love.graphics` font object for measure + draw
- raylib: `MeasureTextEx` + `DrawTextEx`
- SDL3: `SDL_ttf` (e.g. `TTF_SizeUTF8` + `TTF_Render*` / cached textures)

If measurement and drawing use different font metrics, layout correctness is undefined.

## Backend Adapter Interfaces (Target Shape)

Each backend should implement a small adapter API with the same conceptual flow.

### Common Adapter Flow

1. Collect platform input (`mouse`, `keyboard`, `window size`, `delta time`, `scroll`)
2. Normalize into `ArgileFrameInput`
3. Apply explicit state toggles (focus/selected/disabled) using known demo ids
4. Call scene export `ArgileDemoFrameForContext(...)`
5. Iterate render command buffer and draw

### Backend Renderer Adapter Responsibilities

Required command support in first backend set:
- `RENDER_RECTANGLE`
- `RENDER_BORDER`
- `RENDER_TEXT`
- `RENDER_PAINT`

`RENDER_CUSTOM` may be a debug-visible no-op in first demos, but must not crash.

#### Portable Paint Subset Support (mandatory)
- `PAINT_OP_FILL`
- `PAINT_OP_STROKE`
- `PAINT_OP_RECT`
- `PAINT_OP_ROUND_RECT`
- `PAINT_OP_CIRCLE`
- `PAINT_OP_LINE`

### Backend Adapter File-Level Responsibilities (Specific)

#### `backends/love2d/renderer.lua`
- FFI-safe color conversion (`0..1` and byte fallback only if needed)
- Render command dispatch loop
- Paint op drawing helpers
- Text string extraction from `StringSlice`
- Border rendering helper
- No platform event polling here

#### `backends/love2d/demo/main.lua`
- Window loop and input collection
- FFI loading and context initialization
- Arena allocation/free
- Measure-text callback registration (or helper module setup)
- Calls backend renderer module
- Keyboard toggles for demo state flags

#### `backends/raylib/renderer.c`
- Translate command buffer to raylib draws
- Shared helpers for color conversion, radius, line width
- Text draw path using raylib font APIs
- Paint op dispatch implementation

#### `backends/raylib/text.c`
- `MeasureTextFnType` callback wrapper using raylib font/font size state
- Backend-owned font registry or single-font demo path
- Must match draw path font metrics

#### `backends/sdl3/renderer.c`
- Render rectangles, borders, paint using SDL3 renderer APIs
- Text via SDL_ttf helper (`text_sdlttf.c`)
- Avoid dynamic allocations in per-command hot loop where possible

#### `backends/sdl3/text_sdlttf.c`
- Argile measure callback implementation (`TTF_SizeUTF8` or equivalent)
- Text rendering path (texture cache optional first pass)
- Font registry mapping from Argile text config -> SDL_ttf font object

## Scene Export Strategy (Portable and Reusable)

### Current Problem
The existing demo scene is packaged inside `demo/love/v3_bridge.t` and exports a Love-specific frame function.

### Target Strategy
Move backend-neutral scenes into `examples/scenes/` and export generic C-callable functions.

### Required New Scene Modules

1. `examples/scenes/v3_demo_scene.t`
- Main interactive demo scene (card with all runtime states)
- Exports:
  - `ArgileDemoFrameForContext(...)`
  - `ArgileDemoGetIds(...)` (recommended)
  - optional `ArgileDemoInstallMeasureTextForContext(...)` if you want a Terra-side demo measure callback

2. `examples/scenes/v3_conformance_scene.t`
- Deterministic scene for backend command coverage checks
- Includes rectangle/border/text/paint combinations with stable ids and known expected command structure
- No platform-specific behavior

3. `examples/scenes/v3_state_matrix_scene.t`
- Deterministic state overlay scene (hover/active/focus/selected/disabled)
- Used by core correctness tests and backend smoke tests

### Build Integration Options (Choose One and Keep It Clean)

#### Option A (Recommended): Single library includes core + example scene exports
- `tools/build_argile.t` exports core `ui.capi` + scene exports from `examples/scenes/*.t`
- Pro: one `.so` for demos, simpler backend hosts
- Con: demo exports ship in core library unless build toggle exists

#### Option B: Separate example library (`libargile_examples.so`)
- `libargile.so` stays pure core
- `libargile_examples.so` links/exports scene functions and depends on core
- Pro: cleanest separation
- Con: more build/link complexity

### Plan Decision (Recommended)
Start with **Option A** but formalize it:
- move demo export out of `demo/love` and into `examples/scenes/`
- load scene exports from a dedicated list in `tools/build_argile.t`
- no backend-specific names/functions in the exported scene set

This gets a clean architecture quickly without blocking on Terra/linker complexity.

## Testing Strategy (End-to-End Correctness Across Backends)

The repo already has strong core correctness coverage. The portability refactor adds **adapter conformance and portable scene ABI tests**.

### Test Layers (Required)

#### Layer 1: Core Correctness (existing, keep authoritative)
Examples already present:
- `tests/test_integration_v2.t`
- `tests/test_runtime_states_integration.t`
- `tests/test_v3_render_integration.t`

These remain the ground truth for render-command semantics.

#### Layer 2: Portable Scene Export ABI Tests (new)
**New file:** `tests/test_portability_frame_api.t`

Validate:
- `ArgileFrameInput` struct exists and can be used in Terra/LuaJIT FFI (if Lua harness added)
- `ArgileDemoFrameForContext(...)` returns command count > 0
- `ArgileDemoGetIds(...)` returns stable non-zero ids (if implemented)
- Scene export behaves correctly across frames when input/state changes

#### Layer 3: Backend Adapter Conformance (new)

Backends should be verified against a deterministic conformance scene.

**Approach**
- Use `examples/scenes/v3_conformance_scene.t` to emit a fixed command stream
- Add per-backend "replay" or logging mode that records command handling sequence/payload summary
- Compare against expected command coverage and invariants

For example, backend renderer logs could include lines like:
```text
RECT x=20 y=20 w=200 h=80 color=...
PAINT round_rect x=10 y=10 ...
BORDER w=1 ...
TEXT "Title" x=...
```

This is not a pixel snapshot. It verifies adapter interpretation and command coverage.

#### Layer 4: Manual Visual Smoke (first pass)
For each backend:
- window opens
- demo card visible and correctly sized
- hover/active/focus/selected/disabled visibly change card/text/paint
- resize does not break layout

## Required Code Patterns (Examples)

### 1. Generic Scene Export (Terra)

```terra
local ui = require("src.builder")
import "src/lang.argile_v3"

-- scene definition here ...
local compiled_scene = ui.compileResolved(v3_demo_scene_node)

terra ArgileDemoFrameForContext(ctx: &ui.Context, input: &ui.ArgileFrameInput) : int32
    ui.SetCurrentContext(ctx)

    var p: ui.Vector2
    p.x = input.pointer_x
    p.y = input.pointer_y
    ui.SetPointerStateForContext(ctx, p, input.pointer_down)

    ui.BeginLayoutForContext(ctx, input.width, input.height)
    [compiled_scene]
    return ui.FinalizeLayoutForContext(ctx)
end
```

### 2. Love2D Host Loop (LuaJIT FFI) Using Portable Scene API

```lua
local in_frame = ffi.new("struct ArgileFrameInput")
in_frame.width = ww
in_frame.height = hh
in_frame.pointer_x = mx
in_frame.pointer_y = my
in_frame.pointer_down = love.mouse.isDown(1)
in_frame.delta_time = love.timer.getDelta()

argile.SetElementFocusedForContext(ctx, ids.card, demo_focus)
argile.SetElementSelectedForContext(ctx, ids.card, demo_selected)
argile.SetElementDisabledForContext(ctx, ids.card, demo_disabled)

local count = tonumber(argile.ArgileDemoFrameForContext(ctx, in_frame))
local cmds = argile.GetRenderCommandBufferForContext(ctx)
renderer.draw_commands(argile, cmds, count)
```

### 3. raylib Adapter Text Measure Callback (C)

```c
static struct Dimensions raylib_measure_text(struct StringSlice text,
                                             struct TextConfig* cfg,
                                             void* user_data) {
    struct Dimensions out = {0};
    Font* font = resolve_font_from_text_config(cfg, user_data);
    float size = cfg ? cfg->fontSize : 16.0f;
    Vector2 m = MeasureTextEx(*font, text.chars, size, 0.0f);
    out.width = m.x;
    out.height = (cfg && cfg->lineHeight > 0) ? cfg->lineHeight : m.y;
    return out;
}
```

### 4. Backend Renderer Command Dispatch Skeleton (C)

```c
for (int32_t i = 0; i < command_count; ++i) {
    const struct RenderCommand* cmd = &cmds[i];
    switch (cmd->commandType) {
        case RENDER_RECTANGLE: draw_rectangle(cmd); break;
        case RENDER_BORDER:    draw_border(cmd); break;
        case RENDER_TEXT:      draw_text(cmd); break;
        case RENDER_PAINT:     draw_paint(cmd); break;
        case RENDER_CUSTOM:    /* debug no-op */ break;
        default: /* log unsupported command */ break;
    }
}
```

## Risks and Mitigations (Specific)

### Risk 1: Text metrics mismatch causes layout drift
**Mitigation**
- Enforce same backend text path for measure + draw
- Add state/conformance scenes with visible text alignment checks
- Document backend differences clearly

### Risk 2: Scene export ABI gets polluted with backend-specific params
**Mitigation**
- Require all scene exports to accept `Context*` + `ArgileFrameInput*`
- Put backend-specific translation in backend adapter modules only

### Risk 3: `tools/build_argile.t` becomes an unstructured export merge script again
**Mitigation**
- Formalize export categories (`core`, `examples/scenes`)
- Keep backend folders out of build export loading path
- Add generator comments/tests for pointer-target structs and emitted declarations

### Risk 4: Backend demos drift in behavior and controls
**Mitigation**
- Shared demo scene export and ids helper
- Same key bindings and state toggles across backends
- Conformance scene and adapter logging

### Risk 5: SDL3/raylib platform specifics slow down the refactor
**Mitigation**
- Land Love2D refactor first as reference adapter
- Keep raylib/SDL3 adapters minimal and command-complete before adding polish

## Final Acceptance Criteria (Ship-Ready Portability Baseline)

Argile portability refactor is considered complete when all are true:

1. `src/` core remains backend-neutral and builds with `make build` without backend dependencies.
2. A backend-neutral scene export ABI exists and is used by demos.
3. Love2D, raylib, and SDL3 demos all render the same Argile V3 example scene from the same exported scene function(s).
4. Each backend supports `RECTANGLE`, `BORDER`, `TEXT`, and `PAINT` command rendering.
5. Runtime states (`hover`, `active`, `focus`, `selected`, `disabled`) visibly work in the demo across all three backends.
6. Text measurement callbacks are backend-owned and match the backend draw path.
7. Core tests (`make test`) remain green.
8. Generated C header and LuaJIT FFI bindings remain valid and include all required types/structs/functions.
9. Backend architecture and adapter contracts are documented clearly enough for a contributor to add a fourth backend.
